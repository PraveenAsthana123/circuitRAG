# Benchmark — 2026-04-30

Real k6 runs against the host's port 8080 (Flask 404 service —
proves k6 + load-test infrastructure works end-to-end).

## System
- 12-core CPU, 32 GB RAM, ~9 GB free at run time
- ulimit -n 1048576
- Linux 6.17, docker-compose infra running (postgres + redis + qdrant + neo4j + kafka + minio + observability stack)

## 100 VU / 30s baseline
| Metric | Value |
|---|---|
| Requests sent | 6001 |
| Throughput | 195 req/s |
| Iterations completed | 3000 |
| p95 health | 30ms |
| p95 api | 49ms |
| p99 api | 122ms |
| max latency | 126ms |
**Verdict**: comfortably handles 100 VU. p95 well under SLO targets.

## 5000 VU / 10s spike attempt
| Metric | Value |
|---|---|
| VUs declared | 5000 |
| Active VUs (peak ramp) | 570 |
| Requests sent | 15226 |
| Throughput | 380 req/s |
| Iterations completed | 7607 |
| Iterations interrupted | 570 |
| p95 connect-block time | 11s |
| p95 health (combined) | 26s |
| p95 api (combined) | 590ms |
**Verdict**: laptop's TCP stack saturates at ~570 concurrent connections during ramp-up. k6 client itself is fine; OS networking is the bottleneck.

## Path to true 5k+ VU testing
1. Tune kernel: `net.core.somaxconn=65535`, `net.ipv4.tcp_tw_reuse=1`, raise `ip_local_port_range`
2. Run on a beefier VM (16+ cores, 64 GB+ RAM, no other resource-heavy apps)
3. For 10k+: k6 Cloud OR distributed k6 (multi-machine)

## Real platform performance (when target service is UP)
The 100 VU run shows 195 req/s sustained with p95 < 50ms against
a Flask 404 echo. Once the actual api-gateway + sidecar-advisor
stack runs, expect:
- 50-80 req/s p95 < 200ms (LLM-bound paths)
- 200-500 req/s p95 < 100ms (cached / no-LLM paths)
- 1k+ req/s p95 < 50ms (health probe / static)

These are estimates; real numbers come from running the full stack
locally and the load test against it.
